## 0. Decisions (owner, 2026-11-10)

The five open items of the first draft, settled:

1. **Condition 4** as proposed: single-shot, plus at most one revision when a confirmed optimum
   gets at least one checklist flag; the flags go into the revision prompt, with no solver
   feedback. If the revision doesn't reach a confirmed optimum, the original answer stands
   (section 3).
2. **Unused variables:** dropped with a note in every solver condition, each drop logged in the
   run record (5a).
3. **Key disputes:** a problem is checked only when at least 3 of the 4 conditions' majority
   answers agree with each other and differ from the key, the same rule for every condition.
   The certificate is a better feasible solution or proof that no feasible solution reaches the
   key's value, from an encoding written from the text alone and confirmed by both blinded
   judges (5b).
4. **No MDE threshold.** A contrast is a detected difference only if its Holm-adjusted p is
   below 0.05; otherwise it's inconclusive, with its 95% interval, and "no difference larger
   than X pp" is claimed only if that interval lies within +/-X pp. The power tables are design
   information (section 4): H2 is powered for effects of about 15 pp, H1 for about 8 pp,
   because its conditions share every sample's first reply (power.md's H1 rows, added
   2026-11-11).
5. **Dev revision 2 is declared unused:** the checklist stays at revision 1. While building
   the freeze's code, fixing a bug (code not doing what revision 1 specifies) is allowed and
   is logged in `docs/FOLLOWUP_DEV_LOG.md`; changing what gets flagged is not.
6. **(2026-11-11)** An API error in condition 4's checklist or revision call re-runs the pair
   under Amendment 1 (section 3), approved. Confirmed by a mocked test before any dev run:
   conditions 2, 3 and 4 share their first reply for each problem and sample
   (`tests/test_shared_first_reply.py`).
7. **(2026-11-12) Keys** are parsed by format alone, before the run (section 4): explicit
   infeasible or unbounded wording gives that status, a number gives an optimum, and anything
   else leaves the problem out of every condition, listed by label, with n reported. Never "no
   optimum" for an unparseable key. An aggregate format check found all 128 keys are numbers.
8. **(2026-11-12) A reply cut off at `max_tokens`** is scored as that condition's outcome and
   never re-run, since re-running only failures resamples toward success (section 4). The code
   already did this; nothing changed.
9. **(2026-11-12) One run directory for both benchmarks**, each problem named by its label
   (`complexlp:1`, `industryor:1`) in results, resumes, the manifest, the run order and the
   report (section 6).
10. **(2026-11-13) Rounded keys:** an optimum is also right if it rounds to a non-whole key at
    the key's written decimals; whole-number keys stay at 1e-4 (section 4). A precision check
    found 7 non-whole keys, 2 of them with fewer than 5 significant figures. Follow-up only:
    M6's scoring is unchanged.
11. **(2026-11-13) The encoding check's judge prompt** is `docs/followup/judge_prompt.md`,
    frozen with the rest (sections 3 and 5b).

## 1. Hypotheses

Two primary contrasts, each two-sided, Holm-corrected together at a family-wise alpha of
0.05:

- **H1: checklist-triggered revision vs single-shot.** Does revising when the checklist flags
  something change accuracy?
- **H2: single-shot vs the no-solver baseline.** Does formulating and solving change accuracy
  against answering directly? M6 asked this on NL4Opt; this asks it on harder problems.

The other four pairs (baseline vs self-correction, baseline vs checklist revision, single-shot
vs self-correction, self-correction vs checklist revision) are **exploratory**: reported with
the same statistics, labeled exploratory, no Holm, no claims.

## 3. Conditions

Four conditions, each run **3 times per problem** (samples 0, 1, 2: `Cache(dir, sample=n)`),
with the same model and pinned settings:

1. **No-solver baseline:** M6's baseline prompt and answer schema (`baseline.py`), unchanged.
2. **Single-shot:** one formulation, solved and checked (`max_attempts=1`).
3. **Self-correction:** up to 3 attempts (`self_correct.solve_with_revisions`, as in M6).
4. **Checklist-triggered revision** (`checklist-revision`; `agent.run(...,
   checklist_revision=True)`): single-shot, then the formulation checklist at revision 1
   (`checklist.py`, SHA-256 `d8c311c59330e11c8c3699fd4ae51324f33df070aaa214fe157ac30427091f6a`
   as of commit `e213060`; the frozen hash is the one in FREEZE.json).
   - **Trigger:** the single-shot answer is a confirmed optimum (`Result.verified`: see the
     note under "Unit" in section 4) and
     `checklist.review` gives at least one flag. Otherwise there's no revision, and the
     single-shot answer is the answer.
   - **The revision:** one request, self-contained like self-correction's (problem, previous
     reply, feedback), whose feedback lists the flags (`feedback.for_checklist`) and nothing
     from the solver.
   - **The answer:** the revision's if it is a confirmed optimum; otherwise (an unusable reply,
     infeasible, unbounded, solvers disagreeing, a failed check) **the original answer
     stands**. Every revision is logged and costed, kept or not. An API error in the checklist
     or revision call isn't Claude's answer: the pair is re-run (Amendment 1), and the cache
     replays every call that succeeded.

Conditions 2, 3 and 4 send a byte-identical first request for the same sample, so they share
their first reply through the cache: they differ only where they revise. That makes the
pairing tight, and the discordance for H1 comes from revisions alone.

**Frozen in `docs/followup/FREEZE.json`** (written by the owner at approval with `python -m
opt_agent.followup_freeze approve`, as M6's was; the test split is read only through
`followup.load_sealed`, which refuses if any value differs):
- model string `claude-haiku-5-5`;
- temperature: not sent, so the API default, 1 (> 0; Haiku 5.5 accepts only 1), and the
  other pinned settings (`api.THINKING`: adaptive, display omitted; `api.EFFORT`: medium;
  max tokens);
- the system prompts and schemas: formulation, baseline, checklist, explanation, and the

- the encoding check's judge prompt, `docs/followup/judge_prompt.md` (5b), by its own
  SHA-256;
- every source file in `src/opt_agent/` and `requirements.lock` (installed packages at their
  locked versions), and by name, with its own SHA-256, the analysis that scores the run:
  `src/opt_agent/followup_report.py`;
- seeds: the split's (20261109), the problem order's (20261109, section 6), the bootstrap's

## 4. Scoring and statistics

- **Keys** are parsed by their format alone, before the run, never by results
  (`followup.parse_key`):
  - text with no digits and explicit infeasible wording ("infeasible", "no feasible solution")
    or explicit unbounded wording ("unbounded"), not both: that status;
  - a number, once thousands separators, whitespace, a leading currency sign and trailing
    units are removed ("1,234.5", "$1,200", "150 kg/day"): an optimum with that value. A
    non-finite number isn't one;
  - **anything else** ("No Best Solution", "Max: 99", "12 or 13", both wordings): the problem
    is **left out of every condition** before the run (it isn't run), listed by label, and
    the report gives how many (`unscorable_keys`). An unparseable key is never read as "no
    optimum".
- **Unit:** the problem. A sample's answer is right if `followup.is_correct` says so:
  - for an infeasible or unbounded key, that same status;
  - for an optimal key, status optimal and the objective **within 1e-4 relative** (1e-4
    absolute near zero; `followup.TOLERANCE`), **or**, for a key written with decimals that
    isn't a whole number, an objective that **rounds to the key at the key's written
    decimals** (within half a unit of its last decimal place; a tie counts). Whole-number
    keys ("14", "14.0") get no rounding clause, so a missed integrality constraint still
    fails. The report counts, per condition, the answers right only by the rounding clause
    (`right_only_by_rounding`).
  - **Why the clause:** a key rounded to fewer than 5 significant figures can be off by more
    than 1e-4 relative from the exact optimum (a key 4.53 for 4.5333 is off by 7e-4), which
    would mark an exact answer wrong and favor the baseline, which can round as the key
    does. The precision check (2026-11-13, aggregate only: `scripts/key_formats.py`) found
    121 whole-number keys and 7 that aren't: 1 with 3 or fewer significant figures, 1 with
    4, and 5 with 5 or more. So 1e-4 alone wasn't safe for every key.
  - A solver condition's answer counts only if `Result.confirmed`: CBC and HiGHS agree on
    the status (and the objective) and the arithmetic checks pass, whatever the status, so a
    confirmed "infeasible" can be right for an infeasible key. Anything else is wrong
    (loud). `Result.verified`, used by condition 4's trigger and for keeping its revision
    (section 3), is narrower: confirmed **and optimal**, since a checklist compares the
    rows of a model with an optimum. The two names are kept because they mean different
    things. The baseline is scored as in M6's section 2a.
- **A reply cut off at `max_tokens`** (16,000) is a reply, not an API error: it is cached,
  never re-run, and scored as that condition's outcome, since re-running only failures would
  resample toward success. So, as the code does today: a cut-off first reply is an unusable
  reply, wrong (loud), in the baseline, single-shot and checklist revision; in
  self-correction it is revised like any unusable reply, the condition's own pre-registered
  loop (as in M6), not a re-run. In checklist revision, a cut-off checklist gives no flags, so
  there's no revision and the single-shot answer stands; a cut-off revision is not a
  confirmed optimum, so the original answer stands. Each reply's `stop_reason` is in the
  run's attempt log.
- **Per-problem score:** the fraction of its 3 samples that are right (0, 1/3, 2/3, 1).
  Accuracy is the mean over problems.
- **The analysis** is `src/opt_agent/followup_report.py` (`python -m
  opt_agent.followup_report RUN`), tested on synthetic answers (`tests/test_followup_report.py`)
  and on the dev smoke run before freezing. Everything in this section is what it computes.
- **Primary test:** the paired sign-flip permutation test on per-problem score differences,
  two-sided, computed exactly (the null distribution of the sum of +/-|D_i|;
  `stats.sign_flip_exact`, checked against brute force in `tests/test_stats.py`; the power
  simulation uses the same function).
- **Secondary test:** exact McNemar (`stats.mcnemar_exact`) on majority vote (a problem is
  right for a condition if 2 or 3 samples are).
- **Holm** over H1 and H2, separately for each test. The primary test decides the claims.
- **Confidence intervals:** 95% for every difference, by a paired percentile bootstrap over
  problems (10,000 resamples, seed 20261109): for the mean score difference and for the
  majority-vote difference. Accuracy per condition gets a 95% Wilson interval on majority vote
  and a bootstrap interval on mean score.
- **Detected, or inconclusive.** A contrast is a **detected difference** only if its
  Holm-adjusted p is below 0.05. Otherwise it is reported as **inconclusive**, with its 95%
  interval, never as "no difference". "No difference larger than X pp" is claimed only if
  that interval lies within +/-X pp.
- **Design information, not a threshold:** `power.md` gives the minimum detectable effect at
  80% power with the primary test, Holm's first step, n = 121. The two contrasts need different
  models:
  - **H2** (single-shot vs baseline: separate calls, so independent background discordance):
    12 to 17 pp depending on discordance (5 to 20%) and sample agreement. **Powered for
    about 15 pp.**
  - **H1** (checklist revision vs single-shot: condition 4 reuses every sample's first reply,
    so the two differ only where a revision changes the outcome): 5 to 9 pp depending on the
    share of problems a revision makes worse (0 to 2%) and sample agreement. **Powered for
    about 8 pp.** The model changes all of a problem's samples together, the cautious choice
    for a per-problem test.
  - McNemar on majority vote needs more: up to 17 pp for H2 and 13 pp for H1.
- **Also reported:** sample agreement (how often two samples of a condition agree, per
  condition), how often condition 4 triggered and what it changed (flags by type, revisions
  kept and discarded, answers changed right to wrong and wrong to right), self-correction's
  revisions, unused-variable drops (5a), silent vs loud failures, p50/p95 latency, cost from
  logged usage.
- **API errors:** Amendment 1 of the M6 pre-registration, unchanged, per sample.

## 5. Decision rules

### 5a. Unused variables

A variable in neither the objective nor any constraint with a nonzero coefficient is
**dropped** before validation (`schema.drop_unused`, called by `formulate.parse_reply`), with
any zero-coefficient terms that name it, and the model is solved without it. Each drop is a
note on that attempt (`Formulation.dropped`), written to the run's attempt log and to the
answer's result line (`Item.dropped`). It applies to every solver condition, and it is never a
checklist trigger. The formulation prompt is unchanged.

Exploratory: whether answers with a drop are wrong more often than those without (counts and a
Fisher exact test, labeled exploratory).

### 5b. Key disputes

The key may be wrong (the dev key for 82 is).

**Which problems are checked.** A condition's **majority answer** to a problem is the answer
at least 2 of its 3 samples give (the same status, and for an optimum objectives within the
scoring tolerance, 1e-4); with no such pair, the condition has none. A problem is checked
only if **at least 3 of the 4 conditions' majority answers agree** with each other (same
tolerance) **and differ from the key**. The rule is the same for every condition, and no
other problem is checked.

A key is overturned only with all of:
1. **An encoding written from the problem text alone**, without seeing any condition's model
   or answer. Who wrote it is recorded with each dispute.
2. **Both blinded LLM judges confirm the encoding matches the text**, before its solve counts.
   The judges see the problem text and the encoding only: not the key, the conditions'
   answers, or which condition wrote what. **The prompt** is `docs/followup/judge_prompt.md`
   (frozen, section 3): problem text and encoding in; a verdict (match, mismatch, unsure)
   and any mismatched, missing or extra constraints out. Only "match" from both confirms.
   **The judges** are M6's (the pre-registration's Amendment 2), run as M6 ran them and
   recorded in `docs/amendments/DEVIATIONS.md`: the judge of record is Claude Opus 5.5 in a
   claude.ai incognito chat, and the second judge is free ChatGPT in a Temporary Chat, both
   with web search off, a fresh chat per problem. M6's prompts (Amendment 2, and the
   blinded ones of `docs/amendments/AMENDMENT_3.md`, part 2) asked for labels, not whether an
   encoding matches a text, so none of them is used here.
3. **A certificate** from brute force or an exact solve of that encoding: a feasible solution
   that beats the key, or proof that no feasible solution reaches the key's value (the keys
   are objective values with no solution, so there is no key solution to show infeasible).
4. **A check by arithmetic** of that certificate, independent of the solver (every constraint
   evaluated, the objective recomputed).

Every checked problem, overturned or not, is listed with its encoding, the judges' verdicts and
the certificate. **The raw key is the result of record.** The corrected key is a secondary row,
applied to all four conditions alike.

## 6. Run protocol

- **One run**, on the frozen inputs, from the owner's terminal.
- **One run directory** holds all 3 samples (`evaluate --sample 0 1 2`) and both
  benchmarks (`--split followup-test`), so one cap covers the whole experiment. Results, resumes,
  the manifest, the run order and the report name each problem by its label
  (`complexlp:1`, `industryor:1`), since the two benchmarks' ids overlap. The runner refuses
  anything but the whole experiment: every scorable problem, all four conditions, samples
  0, 1, 2:

  ```bash
  OPT_AGENT_LIVE=1 python -m opt_agent.evaluate --split followup-test --all --conditions baseline single-shot self-correction checklist-revision --sample 0 1 2 --out runs/followup-test --cap 6.00
  python -m opt_agent.followup_report runs/followup-test
  ```
- **Order:** problems sorted by the SHA-256 of `"order:20261109:<problem>"` (the id format of
  section 2; `followup.in_run_order`). For each problem, all 3 samples x 4 conditions run
  together before the next problem starts, so a stopped run leaves whole problems, and no
  condition gets the cheaper or luckier part of the budget.
- **Hard spend cap: $6** (`budget.BudgetedClient`, `--cap 6.00`). Projection from the
  condition-4 dev smoke run's per-call costs (2026-11-11; IndustryOR scaled by its mean prompt
  length, 0.69 of ComplexLP dev's): about $3.29, $4.94 with a 1.5x margin; `--plan` gives the
  worst case before the run.
- **If the cap is hit:** the run stops; only problems with every condition and sample complete
  are analyzed, the same set for every condition; the shortfall is recorded in
  `docs/followup/DEVIATIONS.md`, and `power.md`'s n = 121 numbers (H1 and H2) no longer
  describe the study, which the report says.

## 7. Deviations

As in the M6 pre-registration: once approved and frozen, this file isn't edited. A change
before the run is an amendment, dated, with its reason, tagged before any test problem is
opened. Anything that runs differently from what's written here is recorded in
`docs/followup/DEVIATIONS.md` with what was planned, what happened, and what it changes.
Results are reported as they come out, including any condition that doesn't help, and every
number in the README comes from a generated results file checked by a test.
