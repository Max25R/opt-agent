# Project audit, November 2026

**Audited:** commit `6b1a86c` (main, clean tree), on 2026-11-08. **Report only:** nothing in
the repository was changed or committed except this uncommitted file.

**No API calls.** Every shell command started with `unset ANTHROPIC_API_KEY`. All code was
executed in a fresh clone in a temp directory, which has no `.env` (section 7.2 explains why
that matters in your own checkout). The cache replay used a stand-in client that aborts on
any request, so a cache miss would have stopped the run instead of calling the API. None
did.

**Scope:** CLAUDE.md, README, `docs/` (pre-registration, Amendments 1-3, deviations,
`FREEZE.json`, failure log), every module in `src/opt_agent/` and `scripts/`, the tests,
`review/`, `data/nl4opt/` (hand inputs and the generated REPORT.md), and
`results/eval.json`. Two read-only subagents went line by line through the solver/agent
layer and the ground-truth layer. I checked their main claims before including them, and
each item says whether it was verified and how; a few are marked "reported" where I didn't
re-run them.

**Verdict key.** *Keep*: the decision is right. *Document*: keep it, but say it plainly as
a limitation. *Change for M7-8*: worth doing in the next two milestones. *Change for the
follow-up*: needs a new study, since M6 is frozen. Nothing here proposes changing M6.

### Finding 2: verification and self-correction can't reach the failures that happen

- All 30 failures (10 per condition) were silent: a confirmed answer to a wrong model.
  Verification proves the solution of Claude's model, so by design it can't catch them.
- Self-correction is triggered only by an unusable reply or an infeasible or unbounded
  model. On the test run every one of its 21 revisions was a status answer (18 infeasible,
  3 unbounded); Claude returned the model unchanged each time, and no outcome changed. Its
  only changed outcome on either run (`-864701644`, perturbed) came from a flagged loosening
  (`==` became `<=`) that happened to be right.
- **A cheap signal exists in data you already have** (post hoc, so it needs dev validation
  before anyone relies on it). The baseline's direct answer and single-shot's answer
  disagree on 8 of 274 test problems. Those 8 include 3 of single-shot's 10 failures, and 3
  of its 4 that aren't key errors (the two integrality misses and the "prefers"
  constraint). Of the other 5, 2 are baseline-only failures and 3 are `either` problems
  where both answers are accepted. On the perturbed run: 5 disagreements, covering 3 of
  single-shot's 8 failures. The 7 test failures that agree with the baseline include all 6
  key errors.
- *Verdict:* change for M7-8: return a "low confidence" flag from `POST /solve` when a
  direct answer and the solver's answer disagree (one extra, cheap call). Change for the
  follow-up: test a semantic trigger (that disagreement, or self-consistency over k
  samples) as a pre-registered condition.

### Finding 3: the comparison could only have come out null

- Every condition scored 264/274. The largest discordance in any McNemar comparison was 3
  pairs. With exact McNemar and Holm over 6 tests, the smallest p needs about 8 discordant
  pairs all one way (2 × 0.5⁸ ≈ 0.008). With about 10 failures per condition, one
  condition would have had to fix most of another's failures to show anything.
- One sample per pair, at the temperature the API fixes, means run-to-run variance (seen on
  dev: the bakery and volcano problems) is folded into the comparison, unmeasured.
- The README already says the null isn't evidence of equivalence, and that NL4Opt looks
  saturated. Both are right.
- *Verdict:* change for the follow-up: a harder benchmark where the baseline is well below
  ceiling, k samples per pair (report each problem's success rate), and a pre-registered
  minimum detectable effect. If "no difference" is the claim, pre-register an equivalence
  margin.

### Finding 5: right answer, wrong model is invisible to the score

- Blind grading found one (`294897151`: a "prefers" sentence made into a constraint that
  doesn't bind). The README lists two more (`431521997`'s trivial constraint, and
  `-2001553884`, where the *reference* drops a land limit that doesn't bind). Only 40
  models were blind-graded, so there are likely more among the roughly 250 scored right.
- **An automatic check is feasible at NL4Opt's size** (2-4 variables). Find the variable
  mapping between the system's model and the reference (try every permutation: at most
  24), then test whether the two feasible regions are the same. A constraint `a·x ≤ b` of
  one model holds on the other exactly when the max of `a·x` over the other's feasible
  region is ≤ b: one small LP (or IP) per constraint, in both directions. That finds
  missing, invented and loosened constraints whether or not they bind, with no judge.
  Models with extra helper variables need a projection step and would fall back to blind
  grading. (The solver-layer subagent independently proposed the same test for change
  detection; see finding 6.)
- *Verdict:* change for the follow-up: report "model equivalent" next to "answer correct".
  It would also find wrong references, in both directions, which Amendment 3 can't.

### Finding 6: what a public `/solve` endpoint will hit that NL4Opt didn't

The solver-layer subagent generated 400 NL4Opt-like random models (decimal coefficients
such as 0.6, 1/3 and 0.35, right-hand sides up to 1e6, mixed integer and continuous
variables): no false rejections and no CBC/HiGHS disagreements except the first item below.
The verification layer holds on realistic data; these are its edges, and M7 opens the door
to arbitrary input.

- **HiGHS returns fractional values for integer variables with fractional bounds**
  (verified: bare `scipy.optimize.milp`, maximize x, x integer, bound `x <= 2.5`,
  constraint `x >= 1`, returns x = 2.5 with status optimal; 2.0 with presolve off; CBC
  says 2.0). In the pipeline, a correct CBC answer becomes a loud "solvers disagree", and
  `feedback.feasible()` and the IIS use HiGHS too. Latent today: no logged reply and no
  ground-truth model has a fractional bound on an integer variable, and
  `tests/strategies.py` only generates whole-number bounds for integer variables, so the
  property tests can't find it. *Fix:* round integer bounds inward (ceil the lower, floor
  the upper) before both solvers; add fractional bounds and coefficients to the strategies.
- **`pulp.PulpSolverError` is never caught** (verified: `solver.py` has no `except`). If
  CBC exits non-zero or writes no solution file, the exception ends the whole evaluation
  run; in M7 it would be a 500 error. A resumed run would replay the cached reply and stop
  on the same pair again. *Fix:* map it to `Status.ERROR`.
- **Change flags miss real loosenings** (verified by reading `changes.py:53-75`; the
  subagent reproduced each with `compare`):
  - a flipped direction returns early, so its right-hand side is never judged:
    `need: x >= 5` → `need: x <= 1000` reports only "flipped", unflagged;
  - any edit to an `==` row's right-hand side or terms is an unflagged "changed", though
    moving an equation is the most direct way to make an infeasible model feasible;
  - unnamed matches pair a row with the first row that has the same left-hand side,
    ignoring direction and rhs, which gives false flags after a rename and can hide the
    real change;
  - negating a variable's objective coefficient is unflagged, though it silences an
    unbounded direction as surely as dropping the variable (which is flagged);
  - adding or dropping a zero coefficient counts as a change, so the "model unchanged"
    stop doesn't fire (reported).

  None of this touched M6: on the test run every revision came back unchanged. *Fix:* match
  by name, then by left-hand side *and* direction; always judge the rhs; put flips and
  equation edits in a "review" category; drop zero coefficients first. Better still, judge
  loosening by meaning: an LP per old constraint over the new model's feasible region (the
  same test as finding 5).
- **Ray certificates depend on tolerances** (reported; the subagent built a bounded model,
  max x s.t. `x - y <= 0`, `-x + (1+ε)y <= 1`, optimum 1/ε). At ε = 1e-8 HiGHS overrules its
  own correct optimum with a "certified" ray; at ε = 1e-11 both solvers say unbounded, so the
  false answer is confirmed. The long step adds nothing for constraint rows, because the
  tolerance grows with the step (`rays.py:47-59`). Only ill-conditioned models reach this.
  *Follow-up:* exact certificates (round the ray or duals to fractions and check exactly;
  this also gives Farkas certificates for infeasibility).
- **The cache key depends on the installed SDK.** Requests embed
  `anthropic.transform_schema(LPModel)`, so upgrading `anthropic` or `pydantic` misses every
  cached reply. That matters for M8's "reproduce from the cache" story. *Fix:* commit the
  schema JSON and send that. Relatedly (reported, not reproduced): revision requests embed
  feedback computed by HiGHS under 30 s time limits, so a time-out on a slower machine would
  change a request hash and break a key-less replay.
- **Smaller API notes** (verified by reading `api.py`): `retry-after: 0` gives no wait at all,
  where the SDK falls back to backoff, and `retry-after-ms` is ignored; a spend-limit error
  body whose `"error"` field is a string raises `AttributeError` in `spend_limit_reached`.
  Very large coefficients or bounds (1e20 and up) make HiGHS treat them as infinite; the
  schema could reject such magnitudes up front.
- *Verdict:* change for M7, since these are exactly the inputs an open endpoint invites.

### Finding 8: M7 will "unfreeze" M6

- `freeze.fingerprint()` hashes every `.py` under `src/opt_agent/` and `requirements.lock`,
  and `freeze.check()` requires installed packages to match the lock. Adding FastAPI (a lock
  change) or any module in the package changes the fingerprint, so
  `python -m opt_agent.freeze` will report a mismatch and test runs will be refused. That
  part is correct behavior.
- The real risk: a refactor of `scoring.py`, `ground_truth.py` or `report.py` in M7-8 would
  change what `report.build(runs/test)` produces, and no test would notice (section 2.2: the
  committed `report.json` is never compared with a rebuild).
- *Verdict:* change for M7, before writing code. Tag `8f522c0` (the commit both test runs
  ran on; `FREEZE.json` approves its parent `3b39a55`) as `m6-frozen`, document "M6 numbers
  rebuild from that tag", add the rebuild test, and keep the API in its own module with its
  own extra requirements so the study code stays untouched.

### Finding 9: the judge setup is thinner than it reads

- The judge of record (Claude Opus 5.5) is the same vendor as the system and the author of
  the reviews and labels. The second judge (free ChatGPT) has no recorded model or date
  (DEVIATIONS §2). Both ran in chat UIs, so there's no request log to replay.
- The taxonomy prompt kept "the same answer as row N's model" hints, so a judge sees which
  direct answer and which model belong to one problem. The 20/20 agreement is partly
  structural.
- Amendment 3's row (98.5%) is defined by both judges saying `reference`. Here the judges
  were right in a way anyone can check: all 6 are mechanical key errors (sections 1.1 and
  1.2). The README should lean on that evidence, not on the judges' agreement.
- *Verdict:* document (mostly done already); change for the follow-up: pinned API judges
  from two vendors with logged requests, dates and settings, and a human adjudicator for
  every disagreement and every row that changes a number.

### Finding 10: the explanation step is unevaluated

- The one-line pitch (README line 4, and the opening paragraph of CLAUDE.md) includes "explains it". Every
  evaluation run used `with_explanation=False` (`evaluate.py:262`); the live tests are the
  only real-API exercise of it.
- The number checker has gaps too (verified by reading `explain.py:169-171`; the rest
  reported): a whole number passes if any allowed number is within 0.5, so with Wyndor's
  facts every whole number from 0 to 6 passes; `.5` isn't read as a number; `1e5` is read
  as `1`; number words are never checked; and correct restatements such as `36,000` for a
  fact of 36 (thousands) are flagged.
- *Verdict:* document now ("not evaluated"); change for M7-8: run the checker on the dev
  split's verified answers (the formulations are cached, so only the explain calls cost) and
  report how often a number is flagged. Consider placeholders (`{values.doors}`) that code
  fills in, so an invented number can't appear at all.

## 1. Correctness

### 1.1 The integrality rule decided 4 of the 10 failures per condition (high; verified)

**What happened.** The four do-nothing failures, which are every failure in the do-nothing
subset in every condition and 4 of Amendment 3's 6 "answer-key errors", are:

| problem | text | rule label (note) | annotated answer | the systems' answer |
|---|---|---|---|---|
| `431521997` | bubble teas, "mango must outnumber lychee" | continuous ("says 'units of lychee'") | 0 | 36 |
| `1605420061` | crepes, "peanut butter must exceed chocolate" | continuous ("says 'units of chocolate'") | 0 | 20 |
| `-1540907330` | curry bowls, "goat must outnumber chicken" | continuous ("says 'units of chicken'") | 0 | 17 |
| `2078392466` | wine vs kombucha, "wine must exceed" | continuous ("says 'unit of kombucha'") | 0 | 11 |

**The mechanism** (traced in code, and checked against the committed ground truth):
1. `integrality.py` labels a problem continuous when a mention says "units of X", even when
   X names an ingredient of a countable product (the known bug).
2. `ground_truth.integrality_matters` (`ground_truth.py:284`) compares only the
   *annotated* LP and IP optima. For these four both are 0, so no hand label was required
   (`needs_hand_label`, line 279) and the rule's label stood.
3. `build_record` stores the strict reading only when the label isn't continuous
   (`ground_truth.py:131`, "strictness needs integers").
4. So the strict reading (x > y as x ≥ y + 1), which every condition used, was never an
   accepted answer. Lenient scoring doesn't rescue it either: `readings` only offers
   `record.strict` when it exists (line 250).

**Footprint.** These are exactly the 4 scorable test problems that are rule-labeled
continuous by "units of" *and* have strict wording; there are no others. Fixing the label
only adds an accepted reading, so it can't turn a right answer wrong. With correct labels,
all three conditions would be 268/274 (97.8%), not 264/274, and the do-nothing subset
14/14, not 10/14.

**It's arbitrary, not a judgment call.** Three do-nothing problems of exactly the same kind
(`1151835649`, `1268238141`, `-685300642`: countable products, strict wording, annotated
optimum 0) are rule-labeled integer, because their mentions don't name an ingredient. So
they got a strict reading (26, 14, 10) and were scored with it. Pre-registration 3b's "3 of
the 14 have a nonzero optimum under the strict reading" would be 7 of 14. Two tests lock the
current behavior in, since both start from the label:
`test_strict.py::test_every_integer_problem_with_strict_wording_has_a_strict_reading` and
`test_preregistration.py::test_strict_counts`.

**It was known before the freeze.** CLAUDE.md lists the bug as "known and unfixed ...
harmless for the annotated answers; fix after the owner's labels". That was true for the
annotated answers and wrong for the strict reading. The second review judge disputed all
four on 2026-11-04 (they are 4 of the 8 disputed reviews), and the freeze and the test runs
followed the same day. `freeze.unfinished()` had no item for open data bugs.

**Related gap (medium, verified).** Because of the same "annotated reading only" test, a
rule label also picks the "=" reading's answer without a hand check. Of the 8 scorable test
problems with an "=" reading, 2 rule-labeled ones have different LP and IP "=" optima
(`-2015083686`: 1833.33 vs 1760; `-169306566`: 40 vs 32). The labels look right (both count
whole things), but the stated policy, "wherever integrality changes the answer, the label is
a hand label", doesn't hold for the alternative readings.

**Verdicts.**
- *Document now:* the README should say that 4 of the "answer-key errors" are ours: a known
  bug in our own integrality rule that suppressed the strict reading. That's a stronger,
  more honest story than "the key is wrong".
- *Change for M7-8:* fix the rule (match countable product nouns, not ingredient names),
  and make `needs_hand_label` true wherever *any* accepted reading's answer depends on
  integrality, or wherever strict wording meets a rule-continuous label.
- *Change for the follow-up:* rebuild the key with the fix and report the re-score as a new,
  separately labeled result. M6's numbers stay as frozen.
- *Process:* add "no open data bug that touches scoring" to the freeze checklist.

### 1.2 Two more answer-key errors that no check reached (high; verified)

The other two failures that Amendment 3 counts as correct are operator errors in NL4Opt's
annotation that contradict the text:

| problem | text | annotated | key | the text's reading | every condition answered |
|---|---|---|---|---|---|
| `-926961422` | "The company has a total of 6 working hours a day" | `1.2f + 1.2s >= 6` | 559600 | `<= 6`: 14000 | 14000 |
| `-2138755435` | "the restaurant wants to have 4000 customer interactions per hour" | `70c + 85h <= 4000` | 95 (almost no service) | `>= 4000`: 330 (integer); `=`: 425 | 425 |

- **Why nothing caught them:** `nl4opt.py` checks an operator against the text only when the
  text uses a comparative ("more than", "at most"). "Has a total of" and "wants to have"
  aren't comparatives, so the operator went unchecked. The ground-truth subagent counted
  213 such unchecked constraints in scorable test problems, and found only these two
  mismatches.
- **No review either:** `-926961422` isn't in ORLM or ORLMBenchmark and met no review rule.
  `-2138755435` passed the cross-check by the edited-text rule (1.4). The subagent counts 19
  scorable test problems with neither a review nor benchmark coverage (reported, not
  re-counted).
- **Both carry into the perturbed set,** where they're silent failures in all three
  conditions too, which blurs the memorization check slightly.

**What this changes about Amendment 3.** All 6 failures the judges called `reference` can
be shown without a judge: 4 by the integrality mechanism (1.1), 2 by reading one sentence
against one annotated operator. So the exploratory 98.5% rests on firmer ground than "two
LLM judges agreed", and the README can say so. It's still post hoc and stays exploratory.

**Verdicts.** *Document now* in the README's Limitations. *Change for M7-8:* a small lexicon
check on otherwise unchecked operators ("has / available / budget / total of" → ≤; "needs /
requires / must deliver" → ≥) that sends mismatches to review rather than rejecting them.
*Change for the follow-up:* review every scorable problem the benchmark doesn't cover
(absence is itself a signal: its authors dropped 44 test problems).

### 1.3 The strict reading can credit a status on a problem with an optimum (medium; verified)

- `-1394927728` (a wage bill "below $150000") and `1789644271` (grills) have annotated optima
  (150000 and 6) but are infeasible under the strict reading, so "infeasible" is accepted
  through the strict reading.
- In the test run the baseline answered "infeasible" on both and was credited; single-shot
  and self-correction did the same on `1789644271`. All of these count in the "has an
  optimum" subset. (Dev `-1188104412` does the same through the "=" reading; reported.)
- It's mathematically defensible, but section 3e doesn't say a status can be right on a
  problem with an optimum, and a model that is infeasible for an unrelated reason gets the
  same credit.
- *Verdict:* document (the report's "correct by reading" counts include these without
  comment); change for the follow-up: list status answers accepted through an alternative
  reading on their own line, or require the infeasibility to involve the strict constraint
  (an IIS that contains it).

### 1.4 Code-level findings from the line-by-line reviews

**Ground-truth layer:**
- **`strict.step` loses thirds** (verified by reading `strict.py:62-71`). `_exact(repr(x))`
  reads 1/3 as 0.3333333333333333, so `x - y/3 >= 0` gets a step of 1e-16 and its strict
  reading quietly equals the annotated one. Percent-derived coefficients stored with float
  error do the same (`-2138755435` has `0.29999999999999993`). No current strict constraint
  is affected (low; latent). *M7-8:* `Fraction(x).limit_denominator(1000)`, or round to the
  precision written in the text.
- **The edited-text rule compared answers, not texts** (Amendment 3 records this for
  `-2138755435`; the same logic kept `-756853497`, whose key looks right). *Follow-up:*
  treat an edit that changes a number as a disagreement.
- **At 1e-4, an answer one integer step off is accepted** on 2 test and 9 perturbed problems
  (reported). 1e-4 is only used for the sensitivity count, the cross-checks and the
  perturbation's "new answer" test, so primary scores are unaffected; worth a line wherever
  1e-4 is reported (low).
- **Test gaps** (reported): `test_highs_reproduces_every_committed_answer` says it
  re-derives the strict answers but checks only LP and IP, and "=" readings are never
  re-derived for the original splits. `test_rule_agrees_with_every_owner_label` gives the
  rule variable names, not the mentions `build_record` uses, so it can't see the ingredient
  bug.
- **`external_check.match`:** a later exact match silently overwrites an earlier fuzzy match
  of the same problem. Not triggered by the current data (reported; low).
- **Stale generated text in REPORT.md** (verified): "Confirmed by the owner: dev 11 of 12,
  test 0 of 62. Unconfirmed test reviews are in `review/test_reviews/`" (they were judged
  instead), and "the ground truth itself is fine" heads a table that now includes Amendment
  2's two exclusions, which were excluded because their ground truth is in doubt (low).

**Solver and agent layer** (the main items are in finding 6; the rest here):
- **`same_answer`'s tolerance** is 1e-6 relative to the size of the objective's terms, so
  for an integer objective near 1e6 with unit coefficients, CBC and HiGHS one unit apart
  would "agree" (reported; low, cross-check only, not scoring).
- **An integer variable with no whole number in its bounds** (`z` in `[0.2, 0.8]`, objective
  only) is called feasible by CBC's feasibility solve; `_value_or_any_in_bounds` then
  returns 1, outside the bound, and CBC ends in ERROR while HiGHS says INFEASIBLE (reported;
  low; a loud failure, never a wrong answer).
- **IIS time isn't in `latency_s`:** the deletion filter's HiGHS solves run outside
  `solve_s` (`self_correct.py:97`), so self-correction's latency is slightly understated
  (reported; low).
- **A test that can't fail as written:** `test_feedback.py:89-92` waits for a model with 4
  constraints, but LOTION has 3, so `feasible` is always `None` and the described case is
  never exercised (reported; low).

With the data present, the 3 skipped tests pass (84 passed in the three data-dependent files). |

So the published numbers rebuild from the repository alone, and every answer rebuilds from
the cached replies through the frozen code. That's an unusually strong result for an LLM
evaluation.

### 2.2 Gaps

- **Half the chain is tested.** `test_eval_json` checks `eval.json` against the committed
  `report.json`s, and `test_readme_numbers` checks the README against `eval.json`. Nothing
  checks that the committed `report.json` equals a fresh `report.build` plus the Amendment 3
  row, so a stale report would pass CI. *Change for M8:* one test that rebuilds both reports
  (about 3 s) and compares bytes.
- **The rebuild is a three-step order to remember:** report, then `amendment3.py` (or the row
  is silently dropped), then `eval_json.py`. *Change for M8:* one `scripts/reproduce.py` that
  runs all three, plus the cache replay above, which is the "reproduce without a key" story
  milestone 8 plans.
- **The CLI needs a key even when every call is cached** (known; milestone 8). The `api.py`
  docstring says "a finished run can be reproduced without an API key", which is true for
  `evaluate` called from Python and false for the command line.
- **The cache key depends on the installed SDK** (finding 6): an `anthropic` or `pydantic`
  upgrade changes `LP_SCHEMA`, and every replay misses.
- **Dev runs aren't committed** (`runs/dev-*` and `runs/smoke` are local only), so the dev
  numbers in CLAUDE.md and the failure log can't be rebuilt from a clone. *Document*, or
  commit them with `git add -f` as the test runs were.
- **The README number test matches by value, anywhere in `eval.json`** (by design). Small
  whole numbers and common rates match many leaves: "20/20 agreement" would pass with any 20
  in the file (it happens to be right). *Change for M8:* generate the results table from
  `eval.json`, or map each headline number to its path.
- **Installing inside Claude Code's sandbox needs `pip --use-deprecated=legacy-certs`** (and
  `PIP_USE_DEPRECATED=legacy-certs` for the editable install's build step): the same macOS
  trust-store failure CLAUDE.md records for the SDK. Not a repo problem; one line in the
  Gotchas.

## 3. Decisions

Every significant decision, with the main alternative, the trade-off and a verdict. M6's
versions stay as frozen; the verdicts are about M7-8 and a follow-up study.

### Agent design

| decision | main alternative | trade-off | verdict |
|---|---|---|---|
| Structured output into a typed `LPModel` (JSON schema), validated again by Pydantic | Generated solver code (PuLP/Pyomo), or tool calls | Safe, cacheable, checkable and diffable vs. no indexed sets or nonlinear terms; fine at NL4Opt's size | Keep |
| One small model (Haiku 5.5) in every condition | A model ladder (one weaker, one stronger) | $0.52 for both test runs vs. a ceiling where a model that does the arithmetic well leaves the solver nothing to add | Keep as the M7 default; change for the follow-up (add a second model) |
| One sample per (problem, condition) | k samples per pair | Cost vs. measuring run-to-run variance, which dev showed | Change for the follow-up |
| Explain verified answers only, every number traced to a fact | Free-form explanation; placeholders filled by code | Trustworthy numbers vs. sentences that can still be false, and checker gaps | Keep the design; document that it's unevaluated (finding 10) |

### Prompts

| decision | main alternative | trade-off | verdict |
|---|---|---|---|
| Zero-shot formulation prompt with the same integrality rule of thumb Claude used to write the labels | A neutral prompt, or few-shot examples | Fewer integrality misses vs. grader and system agreeing by construction (pre-registration 3f) | Document (already in 3f); change for the follow-up: decouple the labeling rule from the prompt |
| The baseline asks for ≥ 8 significant digits | Score the baseline at a looser tolerance | Same tolerance for everyone vs. a prompt change made after seeing dev failures (dev only, recorded) | Keep |
| Prompts iterated on dev only; one change in total | Tune until dev is clean | Honest test numbers vs. a few dev failures left | Keep (exemplary) |

### Verification

| decision | main alternative | trade-off | verdict |
|---|---|---|---|
| CBC and HiGHS must agree; arithmetic checks; an LP duality certificate; "unbounded" only with a certified ray | Trust one solver | Found five solver problems (each now a regression test) vs. more code and two dependencies | Keep |
| Only CBC's solution is checked; HiGHS contributes a status and an objective | Check HiGHS's solution too | Simpler vs. a HiGHS bug showing up as a disagreement, not as "HiGHS's answer fails a check" (finding 6) | Change for M7-8 |
| Tolerance-based ray and dual checks; no Farkas certificate; MIP optimality rests on agreement | Exact rational certificates | Simplicity vs. ill-conditioned false certificates and one unproven status | Document (done for Farkas); change for the follow-up |
| "Confirmed" means the solution of Claude's model is right, not that the model matches the text | Also check the model (finding 5) | Clear meaning vs. every modeling error passing every check | Keep the definition; add model checks in the follow-up |

### Self-correction

| decision | main alternative | trade-off | verdict |
|---|---|---|---|
| Self-correction's first attempt replays single-shot's reply from the cache | Two independent samples | A clean paired comparison at half the cost | Keep (one of the best decisions in the repo) |
| Revise only on an unusable reply or an infeasible or unbounded model | Semantic triggers: disagreement with a direct answer, self-consistency over k samples, a critic pass | No false triggers vs. no chance to fix silent errors. On test, all 21 revisions were status answers, all returned unchanged, 0 outcomes changed, for 11% more cost | Change for M7-8 (expose a disagreement flag) and the follow-up (a semantic trigger as a condition); finding 2 |
| Up to 3 attempts; stop when the model comes back unchanged | More attempts | Bounded cost vs. little evidence more would help | Keep |
| Flag deletions and loosenings by comparing rows by name or left-hand side | Judge loosening by meaning (an LP per old constraint) | Simple vs. missed flips, equation edits and sign changes (finding 6) | Change for M7-8; say flags aren't verdicts |

### Scoring and tolerance

| decision | main alternative | trade-off | verdict |
|---|---|---|---|
| Score the status and objective, not the model | Model-level checks (finding 5), or graders at scale | Objective, cheap, automatic vs. blind to right answers from wrong models | Keep as primary; add model checks in the follow-up |
| 1e-6 relative and absolute, with a 1e-4 sensitivity count | 1e-4 primary | Rejects near-misses vs. rounding risk; 0 flips at 1e-4 in every condition, so moot here | Keep |
| Accept several readings (annotated, strict, "=") and record which matched | Annotated reading only | Fair to text the annotation scheme can't express vs. accepted answers that depend on the integrality label (1.1) and can be a status (1.3) | Keep; fix both dependencies |
| Score at report time from recorded answers | Score during the run | Re-scoring without paid calls | Keep |
| API errors re-run, wrong only after 3 resume passes (Amendment 1) | Count them wrong at once | Doesn't charge Claude for outages vs. a more complex report | Keep (0 errored pairs in the end) |

### Integrality

| decision | main alternative | trade-off | verdict |
|---|---|---|---|
| One label per problem: all-integer, all-continuous or `either` | Per-variable labels | Two stored optima vs. mixed problems forced into one kind | Document; change for the follow-up |

| decision | main alternative | trade-off | verdict |
|---|---|---|---|
| Build our own key from NL4Opt's annotations; ORLM and ORLMBenchmark as cross-checks only | Use a published key | Provenance and control vs. our own bugs in the key (1.1) | Keep (a portfolio highlight) |

## 4. Code quality

**Overall:** clear and well tested. Small functions, comments that explain why, and every
pre-registered rule traceable to one function. The weak spots are at the edges.

**Tech debt:**
- **The Amendment 3 row lives outside the report**, so every rebuild needs a second script,
  and `eval_json.py` must refuse a report without it (section 2.2). For M8, let the report
  builder take optional extra rows so one command makes the final file.
- **`solver.py` and `highs.py` repeat** `solve`, `_infeasible_or_unbounded` and `_timed_out`
  almost line for line (reported). One shared helper taking the solver's name, its
  `solve_once` and its feasibility function would keep the certified-ray rule identical by
  construction.
- **Four tolerance comparators** (`ground_truth.same_value`, `orlm._close`,
  `external_check._same`, `perturb._same`; reported). One function with a named tolerance
  would do.
- **`ground_truth.py` mixes the scoring core** (`readings`, `matching_reading`) with about
  280 lines of REPORT.md rendering (reported). Since the freeze hashes all of `src/`, a
  wording fix in the report changes the fingerprint.
- **`external_check.py` (583 lines) mixes** matching, rendering, judge prompts and
  `apply_decisions`, which rewrites the hand-written `reviews.json`, `integrality.json` and
  `exclusions.json` (reported).
- **`run_results` imports `Item` and `Manifest` from `evaluate`,** which imports the agent,
  the API layer and the SDK. Scoring a run shouldn't need the client stack; move the two
  models to a small module (low).
- **`evaluate.render` re-implements a slice of the report** (low; labeled a convenience).
- **Three functions named `describe`** (`api.py`, `formulate.py`, `rays.py`; low).
- **Package size:** `external_check.py`, `packets.py` and `ground_truth.py` (26-30 KB each)
  are mostly one-off M6 tooling. After M8 they could move to a `study/` package, so the
  agent package stays small for the API and the Docker image.
- **Hard-coded ids** (`amendment3.COVERED`, `packets.SAYS_LP`, `external_check.HARD_CASES`)
  are right for a frozen study, and each has a test.

**Dead code:** none found worth removing; the owner's unused packets
(`review/integrality_blind/`, `review/says_lp.md`, `review/test_reviews/`) are kept on
purpose, as sent.

**Test gaps:**
- No test that the committed reports equal a rebuild (section 2.2).
- The Hypothesis strategies use small whole-number coefficients, give integer variables
  whole-number bounds, and put every variable in the objective (reported), so fractional
  data, where tolerances matter most and where the HiGHS bug lives, is never
  property-tested.
- Untested behavior: a flip plus an rhs change, `==` rhs edits, left-hand-side matching,
  zero coefficients, objective sign flips, `PulpSolverError`, `wait_s` with `retry-after: 0`
  or an HTTP date.
- `test_budget.py` checks `worst_case_usd` against a re-derivation of itself rather than real
  token counts (reported); only the live smoke test checked the bound for real.
- The two tests named in 1.1 enforce the label-gated strict reading, and the two in 1.4 don't
  test what their names say.

## 6. Portfolio view: the README in 2 minutes

**What a recruiter sees first:** a title, "Status: work in progress", a roadmap, a
Quickstart that needs a dataset download and an API key, then about 160 lines on solver
verification and ground-truth construction. The result, the most interesting thing in the
repo, starts at line 233 of 312.

**What's strong and should be up front:**
- A pre-registered, frozen evaluation whose results file rebuilds byte for byte, and whose
  every answer replays from the cache with no key, for $0.52 in API calls. Few student
  projects (or papers) can say that.
- An honest negative result: the no-solver baseline ties the solver pipeline on NL4Opt
  (264/274 each), and verification caught nothing because every failure was a modeling
  error. That's a real finding about where LLM-plus-solver systems fail.
- Five solver problems found by cross-checking (wrong dual signs, mislabeled statuses, a
  false MIP optimum, false optima with free variables), each with a regression test.

**What's unclear or buried:**
- No 3-line summary at the top: what it does, what the evaluation found, how to see it
  work.
- Heavy internal vocabulary: "says LP", "do-nothing", "strict reading", "judge of record",
  "Amendment 2, part 5". Fine in the docs; too much for the README.
- The `TODO` sections (Architecture, Limitations) make it look unfinished. The diagram is
  planned for M8; until then, remove the empty headings.
- "Claude wrote this code" is disclosed, which is right, but the owner's role (the design
  decisions, the pre-registration, every approval) is only implicit. A short "How this was
  built" note would answer the question a reviewer will ask anyway.

**What's overclaimed or framed loosely:**
- **"Most shared failures are answer-key errors."** True, and more solid than the README
  makes it sound: all 6 can be shown without a judge. But 4 of the 6 come from our own
  integrality rule and 2 from NL4Opt operators that contradict the text. Said that way it's
  a better story: the evaluation found bugs in its own key, and can show them.
- **The exploratory row sits in the headline table.** It's labeled, but tables get skimmed.
  Move it below, next to the pre-registered sensitivity rows.
- **Lenient accuracy and "without disputed reviews" are missing,** though Amendment 2 says
  every accuracy comes with its lenient version. Lenient favors the solver conditions (266
  vs 264 of 274); without the disputed reviews all three are 97.7% (260/266). Leaving out
  the view that favors the system is the opposite of overclaiming, but it's still selective.
- **"No sign of memorization."** The test can only catch an answer recalled for the
  original numbers. It can't catch a memorized *formulation*, since perturbation keeps the
  structure. Say "no sign that answers were recalled rather than computed".
- **"Explains it"** in the first line, without evaluation (finding 10).

**Suggested order for M8:** a summary and the results table (with lenient), one diagram, a
30-second demo (the cached replay, with no key), limitations, then the verification and
ground-truth detail.

### 7.2 A practical note on "no spending"

`config.get_api_key` falls back to `.env` in the current directory. So in your own checkout,
`unset ANTHROPIC_API_KEY` does **not** stop a command from finding a key: `.env` still
supplies one. The budget guard still caps spend, but for a guaranteed no-spend session, run
from a clone without `.env` (as this audit did), or give `get_api_key` an explicit opt-out
such as `OPT_AGENT_OFFLINE=1`. *Change for M8.*
